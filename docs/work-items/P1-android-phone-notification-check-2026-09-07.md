## 실제 사용자 관점의 유료 가치 평가

**현재 확인된 경험만으로는 월 29,000원을 결제하지 않는다.** 실제 수신은 작동하고 조건 저장·이전 분석 연결도 존재하지만, 유료로 약속한 당시 근거 복기의 정확성과 알림 자체의 정보가 부족하다. 다음 세 문제를 결제 판단의 우선 기준으로 고정한다.

### 1. P1 — 과거 알림 복기 화면에 실시간 가격이 섞인다

- 내 감시 조건 → 최근 조건 확인 기록 → 8월 26일 `조건 확인 때 분석`을 실제로 열었다.
- 스냅샷 `2d3acfd0-b54e-441e-b669-179597f041c0`는 8월 26일 15:04:38 KST, 저장 가격은 **79,066**이었다. 그러나 휴대폰 화면에는 같은 과거 기준 시각과 **79,331**이 함께 표시됐다.
- `PerpetualDecisionExperience.tsx`의 `LivePerpetualPrice`가 과거 분석 화면에서도 실시간 ticker 가격으로 덮어쓰는 것을 코드에서 확인했다. 스냅샷 자체가 수정된 문제는 아니다.
- 화면에는 `현재는 오르는 근거가 더 많습니다.`, `분석 가능`, 비활성 버튼 `데이터 정상화 후 가능`이 함께 표시된다. 과거 기록이며 새 감시를 만들 수 없는 이유를 명시하지 않아 과거와 현재 판단을 혼동하기 쉽다.
- 수정 대상: `src/components/coin/PerpetualDecisionExperience.tsx`와 관련 가격/과거 분석 표시. 과거 기준 가격을 유지하고 현재 가격은 별도 이름·시각으로 표시한다. 과거 분석임을 첫 화면에 분명히 표시하고 현재 분석 이동을 제공한다.
- 완료 기준: 같은 과거 링크를 다시 열어 79,066과 당시 근거가 유지되고, 새로고침·실시간 갱신 후에도 당시 가격이 바뀌지 않아야 한다. 현재 분석 화면의 실시간 가격은 유지한다.

### 2. P1 — 조건 알림이 무엇이 바뀌었는지 말해주지 않는다

- 동일 계정의 실제 8월 26일 조건 이벤트 제목은 `판단 변경`, 본문은 `엇갈린 시간대 구조와 큰 금액 체결이 정리되면 다시 판단합니다. 조건이 확인되었습니다.`였다.
- 현재 `monitorNotificationCopy(condition)`도 저장한 안내문 뒤에 `조건이 확인되었습니다.`를 붙인다. 알림 제목에 자산이 없고, 실제 확인 시각·이전 상태·새 상태를 전달하지 않는다.
- 코인 예시는 실기기에서 수신했지만 `변화가 감지되었습니다` 다음에 변화의 증거 없이 Home으로 이동한다. 이는 예시의 한계이며 실제 perpetual 알림까지 Home으로 이동한다고 일반화하지 않는다. 실제 perpetual payload는 해당 스냅샷으로 연결된다.
- 수정 대상: `src/lib/perpetualMonitor.ts`, `src/lib/server/perpetualMonitorScanner.ts`, `src/lib/pushTestMessages.ts`. 실제 평가 스냅샷을 이용해 자산·확인 시각·변화·남은 위험/확인 행동을 작성한다. 시장 조건을 조작하거나 테스트를 실제 성과로 기록하지 않는다.
- 완료 기준: 사용자에게 알림만 보여줘도 무엇이 달라졌는지 설명할 수 있고, 눌렀을 때 동일 사건의 근거가 열려야 한다. 일반 사용자의 첫 성공 경험을 정상 기기 등록 범위 내에서 검증할 수 있어야 한다.

### 3. P2 — 감시가 일하고 있다는 근거와 대기 진행 상황이 숨겨져 있다

- 감시 목록에는 조건과 `감시 중`, 종료 시각, 일시 정지/취소가 표시된다. 서버의 마지막 평가 시각과 아직 미충족인 이유는 표시되지 않는다.
- 실제 서버가 약 5분 간격으로 검사하고 있었지만 사용자는 이를 화면에서 확인할 수 없었다. 원래 큰 흐름/현재 구조 충돌에서 현재 1시간/15분 충돌로 상황이 바뀐 경과도 별도 설명되지 않는다.
- 일반 계정에는 수신 확인 버튼이 없고 `/api/push-test`도 관리자 전용이다. `연결됨`과 실제 기기 수신 확인이 구분되지 않는다.
- 수정 대상: `src/components/coin/PerpetualMonitorManager.tsx`, `src/components/RadarAlertCenter.tsx` 및 필요한 상태 응답. 자체 수신 확인을 추가한다면 현재 기기 지정·횟수 제한·테스트 표시를 유지하고 관리자 도구 권한을 열어서는 안 된다.
- 완료 기준: 저장한 조건, 마지막 확인 시각, 아직 기다리는 이유, 종료 시각이 한 화면에 보이고 사용자 본인이 수신 가능 여부를 확인할 수 있어야 한다.

## 부가 결함과 검증 범위

- 기본 테스트가 `/alerts` 대신 Home으로 가는 원인은 `resolvePushTargetPath`가 명시된 `/alerts`보다 `market=crypto`를 우선해 `/crypto`로 보내는 것이다. 실제 수신·클릭과 코드에서 일치했다. 수정 시 기존 알림 종류별 경로를 회귀 검증한다.
- 기본 테스트는 실기기에서 받았지만 DB delivery_status=pending, sent_count=0이었다. `recordPushTestEvent`는 payload.sent=1만 기록한다. 이 값으로 기기 수신 실패를 판단해서는 안 되며 진단 집계도 정리할 필요가 있다.
- 알림함에 `push test`, `macro` 같은 내부 분류명이 사용자 배지로 노출된다.
- 실제 과거 일정 기록에는 같은 발표 시각의 동일 지표가 반복 기록된 사례가 있다. 당시 이 폰에서 여러 번 받았다는 뜻은 아니며, 발송/기록 중복 여부를 따로 조사해야 한다.
- 현재 휴대폰의 Pro 안내에서 월 29,000원 자동 갱신, 조건 1개→최대 20개, `알림 당시 근거를 다시 봅니다`를 확인했다. 구매 버튼을 누르거나 결제를 실행하지 않았다. 관리자 계정의 All Market Pro 권한은 신규 구매 성공의 증거가 아니다.
- 기본 감시 1개의 유용성이 확인되기 전에 감시 개수를 20개로 늘리는 설명만으로는 결제를 설득하기 어렵다. 위 정확성·정보 전달·신뢰 문제가 해결된 동일 흐름으로 다시 판단한다. 새 기능 개수나 수익률 보장을 추가 통과 조건으로 삼지 않는다.
- 최초 실기기 검사는 운영 설치본의 QA 및 평가였으며 당시 앱 코드는 수정하지 않았다. 이후 사용자 수정 지시에 따라 아래 변경과 검증을 진행했다.

## 후속 수정 — 운영 반영 전 구현 기록

- 과거 알림/뉴스 분석에 복기 안내와 `당시 판단`, `당시 가격`을 표시하고 스냅샷 가격을 고정했다. 해당 화면의 실시간 ticker 갱신과 최신 뉴스 혼합을 차단했다. `현재 분석 보기`에서 현재 시세 갱신을 이어간다.
- 과거 분석의 새 감시 버튼을 현재 분석 안내로 바꿨다. 복기 저장은 원래 snapshot/monitor 연결을 유지한다.
- 실제 조건 알림은 평가 스냅샷을 사용해 자산, KST 시각, 이전→새 판단 또는 확정봉 종가와 저장 기준, 남은 위험을 알린다. 감시 조건과 확정봉 평가 규칙은 변경하지 않았다.
- 감시 목록에 마지막 검사 시각, 미충족 이유, 다음 확인 예정, 데이터 부족/지연을 표시한다. 열어둔 목록만 1분 간격으로 새로 읽고 숨긴 탭에서는 요청을 중단한다. 상태 조회는 현재 사용자 감시가 참조한 분석의 품질·시각·제목만 일괄 조회하며 Pro 세부 수치를 추가 노출하지 않는다.
- `저장된 감시 보기`는 현재 화면에서 목록을 펼치도록 바꿔 hash 경로의 재탐색으로 목록이 닫히는 동작을 없앴다.
- 일반 계정도 현재 기기에 고정된 기본 수신 테스트를 보낼 수 있다. 서버에서 사용자/기기 소유와 enabled Android FCM 조건을 함께 검증하며 5분 3회 공용 제한을 적용한다. 관리자용 시장 예시 권한은 유지한다.
- 발송 응답을 기기 수신 확인으로 표시하지 않는다. 네이티브 수신/열기 콜백이 발생해야 기기 확인 시각을 기록한다. 기본 테스트는 Home 대신 알림 목록으로 연결하고 `수신 테스트` 배지를 쓴다.
- 테스트 발송 로그에 delivery_status=sent, sent_count=1을 기록하도록 보완했다. 이 상태는 FCM 발송 성공이며 기기 수신 증명과는 다르다.
- 네이티브 기기 상태는 첫 렌더링 이후 읽어 서버 HTML과 모바일 초기 화면이 달라지는 hydration 오류를 수정했다.

### 후속 검증 근거

- `npm.cmd run test:push-targets`: 안전한 목적 경로, 상태/지연 표시, 일반/관리자 권한, 현재 기기 지정, 공용 제한, 발송 로그 통과. 실제 route 함수를 실행하고 외부 Auth/DB/FCM만 모의 처리했다. 외부 푸시는 발송하지 않았다.
- `npm.cmd run test:perpetual-snapshot`: 상태/가격/압력 알림 문구와 기존 확정봉·스냅샷 행렬 통과.
- `npm.cmd run test:perpetual-monitors`: 저장 한도, 트리거, 전달, 보존/삭제 행렬 통과.
- `npm.cmd run smoke:billing`: 구독 권한과 결제 경계 통과. 상품/가격/권한 정책을 변경하지 않았다.
- 브라우저 조건 알림의 신선도·중복 방지·계정 구분 회귀 검사 통과.
- 운영용 빌드와 타입 검사 통과. 첫 빌드에서 새 코드의 Set 반복 문법이 프로젝트 target과 맞지 않아 Array.from으로 수정한 뒤 통과했다.
- 실제 저장소에 새 상태 조회를 읽기 전용으로 실행해 HTTP 200과 필요한 4개 필드를 확인했다. Vercel 운영 환경에 기존 KV 공용 제한 변수 이름이 있는 것을 확인했으며 값이나 설정은 변경하지 않았다.
- 외부 Chrome의 360/390/508px 모바일 검증: 과거 가격 79,066이 다른 실시간 가격과 재접속에도 유지됨, 현재 가격은 계속 갱신됨, 복기 저장 시 snapshot/monitor/source 연결 유지, 미충족/데이터 부족/지연 표시 확인.
- 네이티브 연결 모의 환경: Basic 수신 확인 버튼 노출, 관리자 도구 숨김, 현재 기기만 요청, 발송과 수신 표시 구분, 클릭 콜백에서 알림 목록 이동 확인. 물리적 FCM 수신 검사를 대체하지 않는다.
